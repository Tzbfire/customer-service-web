# 知店 · 商家 AI 客服工作台

面向同一家商家团队的网页版客服系统：多个客服账号共享店铺，使用商家自己的大模型接口和商品资料。

## 打开与启动

本次已安装依赖，可在本目录双击 `启动.cmd`，或运行：

```powershell
uv sync --frozen
uv run python -m desk
```

浏览器访问 `http://127.0.0.1:8765`。第一次访问自行创建管理员，没有预设密码。管理员可在「团队成员」创建客服账号。

要求 Python 3.12、uv。Windows 的扫码登录优先使用已安装的 Chrome / Edge；无浏览器时运行：

```powershell
uv run playwright install chromium
```

## 接入你的模型和资料

1. 打开「模型配置」，填写已有的 API Base URL、模型名称和 API Key。
2. 点击「保存配置」，再「测试已保存的连接」。当前适配 Chat Completions 兼容接口。
3. 图片、扫描件或含图片的 Office 文档需要开启图片识别，并填写支持 `image_url` 的看图模型。留空则使用文字模型。
4. 在「知识库」上传资料，按需填写拼多多商品 ID。全店通用政策可以不填商品 ID。
5. 等待识别完成，打开「审核入库」，核对文字、数字、单位、适用条件和商品对应关系，确认后入库。
6. 在「问答测试」提问，核对回答和右侧引用来源。此页面不会发送消息给买家。
7. 到「店铺连接」点击「浏览器登录」，在弹出的独立 Chrome / Edge 窗口中完成扫码或账号登录；系统核对店铺身份后保存登录态。也可导入浏览器导出的 Cookie JSON。
8. 点击「连接消息」。默认采用 AI 草稿模式，客服在接待工作台接管会话、编辑草稿后发送。

图片和扫描资料会发送到配置的模型接口进行识别；回答时发送必要的知识片段、客户问题及最近上下文，使用你的 API 额度。

## 资料能力与范围

- JPG / PNG / WEBP：按图片原始像素分块识别，长图不会先缩成一张小图。
- PDF：提取文字；扫描页、含图片页面交给看图模型。单份最多 40 页。
- Word `.docx`：提取段落、表格及内嵌位图；矢量图片建议先导出 PDF。
- Excel `.xlsx`：提取表格及内嵌位图。最多 15000 行，公式保留为公式文本，需要人工核对其实际值。
- TXT / Markdown / CSV：本地提取文字，支持 UTF-8 和 GB18030。
- 单文件最大 25 MB；单图最多 4000 万像素、20 个识别片段；单份 Office 文档最多 20 张内嵌图片。
- 当前是按店铺、商品 ID 隔离的分块检索，使用中文分词与 BM25 排序；没有向量数据库，也不会训练或微调大模型。
- 仅审核后资料参与检索。没有依据、商品不明确或要求人工的回复进入人工处理。
- AI 引用有助于审核，但不能保证模型每次都正确理解资料。请先用真实问题测试。

## 团队与接待

管理员可以配置模型、连接店铺、维护知识和管理账号；客服可以查看资料、测试问题、接管会话并回复。当前面向同一商家内部协作，成员共享本商家的所有店铺，不是对外多租户 SaaS。

接待方式：

- 人工接待：只接收消息。
- AI 草稿：生成回复草稿，由客服核对后发送。
- 自动回复：仅对支持的买家文字消息、模型判断资料充分且引用有效的情况发送。退款申请、赔付、投诉等进入人工处理。

人工接管会暂停该会话的自动回复，生成中的旧答案会被丢弃，人工回复不会等待模型生成结束。这里的「接管」是本工作台内的协作状态，不会自动调用拼多多的客服转接接口。

消息按平台 ID 去重。人工发送带请求标识，相同标识不会重复发送；平台响应超时会显示「发送结果未确认」，需要在商家后台核对。系统不会盲目重发。

当前拼多多渠道支持接收新推送、文字回复、商品关联和断线重连。买家图片、视频与未支持的卡片进入人工处理；首次连接不导入全量历史；后续从本机保存的序号恢复增量消息，恢复消息进入人工处理。登录过期后需要重新登录，服务重启后需要手动连接。不要让两个程序同时自动接待同一个账号。

## 多人部署

同一台电脑可用不同浏览器分别登录。局域网部署在创建管理员之后运行：

```powershell
uv run python -m desk --host 0.0.0.0 --port 8765
```

其他电脑访问服务器的局域网地址。正式的多人远程部署请使用 HTTPS 反向代理，并设置 `DESK_SECURE_COOKIE=1`。保持单个服务进程（`workers=1`），因为平台连接和登录浏览器由该进程持有。

默认数据在 `.data/`：SQLite、上传原件、登录浏览器配置和本地加密密钥。`DESK_DATA_DIR` 可以指定另一目录。API Key 和店铺 Cookie 经 Fernet 加密保存，密钥由同一服务器文件保护；迁移或备份必须同时保留数据库、原件和 `secret.key`。不要公开此目录或提交进 Git。

若忘记工作台密码，可在服务器本机运行 `uv run python -m desk.admin 用户名`，交互设置新密码并撤销原登录会话。

## 独立浏览器登录

「店铺连接 → 浏览器登录」会在运行客服服务的电脑上打开独立的 Chrome / Edge 窗口。在拼多多真实网页里完成账号输入、扫码及验证，系统自动核对店铺身份并保存登录态，完成后关闭该登录窗口。输入由浏览器原生处理，账号密码不经过网页工作台的输入代理。

网页会显示打开中、等待登录、核对身份、成功或失败。支持显示已有登录窗口、取消登录和重新打开。关闭浏览器会结束本次登录；等待超过 10 分钟会超时；店铺身份核对失败会显示具体失败阶段，不会一直停在等待扫码。

这是交互式桌面登录方式：浏览器在服务器电脑打开，远程使用工作台的其他成员不会在自己的电脑收到该窗口。管理员可在服务电脑完成一次登录，其他客服继续从网页协作。

已移除旧截图遥控的页面、输入转发接口和相关组件。旧版本源码保存在本机 `.data/backups/remote-login-preview-*.zip`，未包含账号凭据。

验证：`uv run pytest -q`（38 项）及 `node --check desk/static/app.js`。新增检查覆盖可见浏览器启动参数、登录识别后关闭窗口、已有窗口显示和取消任务；真实账号验证仍由用户完成。

登录完成判定使用当前页面的域名和路径，登录页查询参数中的 redirectUrl 不会被当作已登录。对应回归覆盖登录重定向中含 chat-merchant 的情形。

## 历史会话与聊天记录

在「接待工作台」切换到「历史会话」，读取当前店铺的平台历史会话。每页 20 个，可加载更多，并按买家或内容筛选已加载的会话。平台未提供准确总数时，明确显示已加载数量与是否还有更多。

选中会话后显示原始消息时间和方向，区分买家、客服及系统消息，展示文字、商品/订单信息与图片/视频链接。聊天记录按消息 ID 向前分页，可继续加载更早消息，显示已加载条数或完整会话条数。

历史浏览为只读，不会调用 AI、发送消息、修改接待方式或推进本地同步游标。点击「接管并回复」才导入该会话最新一页至本地，并由当前客服接管；导入按平台消息 ID 去重，不覆盖已有消息或触发自动回复。其他客服已接管的会话会拒绝冲突操作。

实时会话的本地聊天记录也支持更早分页，按平台消息时间排序，避免旧记录后导入时排错顺序。

已用真实店铺验证两页会话各 20 条，以及历史消息分页无重复。自动回归覆盖历史只读、消息方向和时间、分页、显式接管导入及本地时间排序（当前 43 项）。


## 买家昵称

实时接待、历史会话、聊天标题和买家消息标签优先显示平台提供的昵称，用户 ID 作为会话详情的辅助信息。会话消息中的 `user_info.nickname` 优先解析；缺少昵称时，通过当前买家资料接口补查，并按店铺、买家与聊天类型缓存。新消息没有昵称时保留已有昵称，资料查询失败不会阻断接收，也不会反复立即重试。

昵称可能由拼多多脱敏为带星号的文本，按平台原样显示；平台确实没有提供时明确显示用户 ID。历史查询只更新昵称缓存及已有会话的显示名称，不导入消息、不改变接待方式。

2026-10-28 实测：目标店铺最近 20 个历史会话及 5 个本地会话均取得昵称，网页已确认昵称与用户 ID 分别显示。新增 8 项昵称测试，相关功能回归 42 项通过。截图、验证计数及数据库备份只保存在本地 `.data/`。

## 店铺删除和全部对话导出

「店铺连接」每张店铺卡片包含“删除店铺”和“导出全部对话”，仅管理员可操作。

- 删除需完整输入店铺名称确认。停止消息和登录任务、清除该店铺保存的 Cookie 与同步状态，然后移入“已删除店铺”。知识库、上传文件和本地对话保留；可恢复，恢复后重新登录拼多多。平台上的店铺、消息不受影响。正在发送、解析或导出的店铺暂不能删除。
- 导出默认逐页读取当前平台账号可访问的会话及每个会话的完整消息分页，与本地保存记录合并、按平台消息 ID 去重。也可选择“仅本地”，无需拼多多登录。
- 后台显示会话数、完成数和消息数；可暂停、继续，失败或重启后保留分页进度。导出不会调用 AI、发送消息或接管会话。
- 下载 ZIP 含 `messages.csv`（UTF-8 BOM，可用 Excel 打开）、`conversations/*.json`、`conversations/*.html`、`conversations/*.md`、全部对话 `messages.md`、Markdown 目录 `index.md`、`index.html` 和范围说明 `manifest.json`。图片和视频保留在线地址，不打包媒体原文件。不会导出 Cookie、API Key 或数据库。
- “全部”指平台枚举接口返回且当前账号有权读取的历史，加上本地记录，不代表平台长期留存的所有消息。导出过程中产生的新消息不保证进入此次导出，可重新导出获取最新记录。

导出文件与分页检查点只保存在本地 `.data/exports/`。删除、恢复、导出、权限与分页续传已由自动测试验证；完整后端回归 76 项通过。


Markdown 导出保留买家昵称、ID、聊天时间、角色、文字、引用、商品及订单字段，并使用在线图片或视频链接。每个会话有独立 `.md` 文件；店铺卡片还可直接“下载 Markdown”获取全部会话合并的 `messages.md`。聊天正文使用自动匹配长度的代码围栏保留原文，避免消息中的 Markdown 或 HTML 影响导出结构。

Markdown 实测：从已有平台导出检查点生成 285 个会话文件，合并 Markdown 含 5,081 条消息；未重新请求平台历史。Markdown 与店铺导出相关 11 项测试通过。


## 商品同步与 AI 商品知识

「知识库 → 同步店铺商品并入库」读取当前登录店铺的在售商品列表和详情，保存本地快照，自动建立专属商品资料。包括商品名称、商品 ID、链接、文字描述、注意事项、分类、参数、在售 SKU 组合及同步参考价；详情图片保存地址并支持预览。平台没有提供的事实不会推断。

- 商品详情必须同时匹配请求的商品 ID 和当前店铺 ID。知识按店铺与商品 ID 隔离，与手工上传的商品资料及通用政策一起检索。
- 结构化商品资料自动入库；同步过程不调用模型。价格只作同步快照参考，实时价格、库存、发货及售后承诺仍以平台页面和已审核政策为准。
- 重复同步更新同一份专属资料；手工上传的知识不覆盖。已人工编辑过的商品知识保留，提示平台快照已更新；请自行核对两者差异。完整在售列表未再返回的旧商品，其同步知识会停用；不会据此断言平台商品已删除。
- 点击商品的“识别详情图”，确认后使用已配置的看图模型（可能产生多次 API 调用与费用），结果进入待审核资料。确认入库后，图片中的施工方法、注意事项等才能用于回答；重试会复用已识别图片，同样内容不重复建资料。

## 本地关键词开关与上下文追问

「模型配置 → 使用本地关键词检索」控制实时接待与问答测试：

- 开启（保留原默认行为）：先本地关键词检索。没有命中资料，或多个商品仍需确认时，可以直接返回人工确认而不调用模型。
- 关闭：完全跳过关键词检索，把当前商品范围内已入库资料与历史上下文提交模型理解。即使无资料也会调用模型澄清来意；缺少引用时仍不能自动发送商品事实。关闭不会允许混用店铺、未审核资料或编造商品参数。

资料按商品与店铺隔离，模型理解模式的资料预算为 60,000 字符，超过时按文档分配片段并明确提示模型仅获得部分资料，不静默声称已经读取全部知识。关闭可能增加 API 输入用量。

商品 ID 可从本轮提问或前文的买家消息识别，并在测试输入框中延续；“详细介绍一下”等省略追问会沿用已明确的商品。本次回答依据区同时显示模式及是否调用模型。旧版本客户端保存其他模型配置时，不会重置已选择的关键词开关。

## 多模态图片识别兼容与恢复

详情图识别使用同一个 Chat Completions 多模态接口：发送文字说明和 `image_url` 的 Base64 图片（JPEG），不是独立 OCR 服务，也不要求更换模型。明确请求非流式 JSON，接受字符串正文及可见文字内容块，不把推理内容写成商品事实。

图片识别遇到连接中断、超时、429/服务端临时错误或损坏的 JSON 返回时，最多尝试 3 次；鉴权错误、拒绝及输出截断不盲目重试。错误会区分 HTTP、连接、JSON 和正文缺失等阶段，并标明失败的第几张详情图，不回显服务端可能包含敏感数据的完整错误正文。已完成图片缓存保留，可在重试时复用。

2026-10-28 用当前已配置的多模态模型实际识别某款商品的 8 张详情图，生成 1,706 字待审核资料；未自动入库。原先失败未保留原始响应，无法追溯其唯一原因；此次单图和整批复测均成功，重试及异常分支另有确定性测试。完整后端回归 100 项、前端渲染 5 项通过。


## 聊天、订单与复购总结

会话标题旁新增“查看订单”，只读读取当前买家的近期订单和平台可访问历史订单。近期 `/latitude/order/userAllOrder` 与更早的 `/latitude/order/userHistoryOrder` 分开分页，再按订单号去重；读取失败或分页不完整不会解释为没有购买。保留商品 ID、SKU、规格、购买件数、下单时间和支付/订单状态，不保存接口中的地址、电话、物流联系人等无关字段。历史订单可能没有 SKU ID，按实际返回的商品和规格显示。

知识库每个商品的“聊天＋订单总结”使用最近一次完整平台聊天导出快照：先显示关联案例数和预计模型批次，确认后才查询相关买家订单、提交给已配置的文字模型。每个案例包含按商品卡片划分的咨询、面积原话证据、分规格件数及订单时间线。复购由不同有效支付订单计算，5 件的一笔订单不等于 5 次购买；退款/取消/状态未知的订单不算作有效支付购买。历史多笔购买与指定咨询时间之后的再次下单分别显示，不能由购买量反推通用覆盖面积。

模型提取的面积必须逐字对应买家消息；总结问答必须有客服原文及案例/消息引用，伪造引用会拒绝写入。发送给模型前去除结构化买家/订单编号，并过滤常见手机、身份证、订单号及有标签的联系资料；自由文本不能保证穷尽所有个人信息，执行前应核对使用范围。后台支持暂停、继续，已完成订单与模型批次可复用。结果保存为待审核商品资料，不自动发布；“查看案例与来源”可核对本地原文映射。确认入库后才参与客服回答。知识不修改客服人设。

本轮按用户要求不运行真实聊天蒸馏或总结；完整模型→审核→入库流程由模拟模型测试验证。真实只读验证曾取得同一买家的 1 笔近期＋3 笔更早订单，并核对存在同款多笔已支付订单；不会将此结果泛化为所有买家的完整终身购买历史。
